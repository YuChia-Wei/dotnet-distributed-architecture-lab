# Audit and comparison method

## Scope and evidence

Resolve the requested operation, named context files/roots/rules, relevant
project authority, question and intended behavior. Expand only to a concrete
dependency needed to assess a claim. Product source/tests, dependencies,
generated build output, secrets and unrelated history are excluded by default.
Product-code review belongs to its selected capability; do not expand a context
audit into that work. Use only permitted, necessary non-sensitive evidence.

Identify each subject by project/path and revision or observed file identity.
Record freshness time where material and any uncommitted content: HEAD alone
cannot identify dirty bytes. Separate active adopted project rules, package
baseline, project customizations, source-only policy, historical records and
suggestions. Read the relevant owner statements; do not infer authority or
precedence from filenames, installation or a report's compliance assertion.
Unknown semantic authority remains unresolved for the affected conclusion.

Optional graphs and indexes can guide discovery when their source revision and
coverage are known. Verify material claims against direct selected sources.
Missing results do not establish absence. Use a bounded direct inventory/read
when needed and report uncovered scope; no index installation or universal
rule scan is required. An unavailable evidence source is a limitation, not a
reason to block unrelated project work.

## Audit

1. Confirm scope, exclusions, intended behavior and relevant authority. Read the
   actual selected content and direct dependencies before drawing conclusions.
2. Look for consequential contradictions, ambiguous ownership, stale/broken
   references, duplicate normative owners, unsupported execution claims and
   drift from a supplied baseline. Explain the concrete trigger and effect on
   the requested behavior; a stylistic preference alone is not a defect.
3. Verify each material claim against its source and distinguish observations,
   inferences and missing evidence. Consider plausible alternative explanations.
   A project-specific rule may intentionally differ from the package baseline.
4. Return prioritized actionable findings with location, trigger, impact,
   supporting evidence, confidence/uncertainty and a bounded next action.
   Include checked coverage, exclusions and checks actually performed or not run.
   No supported findings within this scope is not a global health certificate.

Keep the audited bytes read-only. Even a nominal validation command may write;
execute only task-authorized checks compatible with that boundary. Do not fix a
finding, update a ledger or change tracking state during audit. A remediation
request can receive an actionable change proposal for its authorized edit owner.
Governance need not be installed to make that handoff useful.

## Compare

Read the two identified subjects, or the prior report and current subject, plus
the selected findings and comparison question. Preserve existing report/finding
identities and prior conclusions. Cite retained finding labels with their report
identity/path and immutable revision or digest where available; do not allocate
global finding IDs or infer a shared identity from similar titles.

For each selected finding report one current observation:

| Observation | Required explanation |
| --- | --- |
| Confirmed | Current evidence still supports the prior claim in the selected scope. |
| Changed | Evidence, applicability or impact differs; state what changed and what remains. |
| Resolved | Actual current evidence addresses the original trigger and relevant criterion; state the limit of that evidence. |
| Unresolved | Missing baseline, authority, coverage or other required evidence prevents a conclusion. |

Record newly observed issues separately and disclose comparison exclusions.
Do not reconstruct an unavailable baseline from a filename, assume resolution
from changed bytes, or rewrite the prior report's conclusion. A comparison's
current resolution observation does not finalize the old record, close its
tracking item or adopt a rule. Same-agent comparison is not independent review;
any claimed independence needs actual execution evidence and the project's
selected review contract. Report unavailable independence honestly.

## Output, export and project formats

Default to useful conversation prose: subject/scope, findings and evidence,
uncertainty, coverage/checks and next actions. A caller template is inert
presentation; retain source, identity and status distinctions and expose any
conflict or unrepresentable fact. Never fill approval or evidence placeholders
with invented facts. No requested destination means no file write.

For an explicitly requested export, use the selected project-owned destination
outside the audited bytes. Resolve a missing destination from project convention
or prepare the content and seek the destination. Inspect containment, links,
ownership, current contents and concurrent changes before writing. Preserve
unrelated work and final conclusions; reconcile collisions/staleness instead
of overwriting. Read back actual exported content and report its path. These
instructions supply no lock, compare-and-swap or multi-file transaction.

A selected structured format requires its name/version, existing owner, public
operation, destination and lifecycle intent. Map semantic observations to its
supported fields; use only owner-supported operations under actual authority.
The format owner retains identity allocation, writer, reader/query, validation,
finalization, version and migration. Preserve IDs, creation times, assessed
subjects, final conclusions and supported revision/successor relationships.
Unknown or unsupported contracts yield prose plus a field mapping; leave records
intact. Do not invent a parser, assessment schema, allocator, store, query index,
finalizer or arbitrary record patch. Prose export is not a validated assessment.

Follow actual project requirements and selected tracking; this package adds no
mandatory workflow, Issue, audit receipt or storage convention. Preserve failed,
unavailable, deferred and not-run states separately from passed checks. Export,
syntax validity or a commit proves no behavior, acceptance or mechanical finality.

## Existing owners and absence

Neither this package's selection nor its absence changes active project/source
policy. Historical and finalized assessments, customization ledgers and pending
legacy transactions retain their existing owners and supported recovery paths.
Do not convert, delete, resume or finalize them as an audit side effect. Report
encountered unresolved recovery state to its original owner.

Source catalog/release/CI administration, managed installation/update, lock or
projection repair and migration belong to their separately selected owners.
Audit may report scoped drift evidence without repairing it or implying that
older duties have retired. Missing requested tools, formats, runtime support or
review coverage remain explicitly unavailable; return the useful bounded result.
