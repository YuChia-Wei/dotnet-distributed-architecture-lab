# Context maintenance method

## Intake and ownership

Select `propose` or `apply`, the concrete problem/request, intended behavior,
files and relevant authority. Read only selected owner statements, current
contents and dependencies needed for the action. Identify project/path and
revision or observed file identity; disclose dirty content because HEAD alone
does not bind it. Distinguish adopted project rules, package baselines, custom
content, source-only policy, historical evidence and suggestions.

Determine ownership from actual project declarations and relevant managed
ownership evidence, not a folder name. Project-owned instructions, standards,
prompts, templates and links can be edited within actual task authority. Root
entries and unowned runtime files may be project-owned; their name alone proves
neither protection nor writability. A selected root edit does not authorize a
broad replacement or framework cutover.

Managed core, exact generated projections, installation locks, component
selection/version, installation configuration and recovery stores stay with
their source/installation owners. Supply drift evidence to that owner; do not
repair a lock to bless changed bytes, modify generated output, copy core into
custom as a bypass or create a shadow rule. A custom override has effect only
where an actual project/runtime binding supports it. Unknown ownership or
precedence blocks the affected write; continue useful scoped analysis.

Credentials, provider settings, product source/tests and unrelated data are
outside this edit radius. Installation, update, migration, framework-wide
wrapper generation, source catalog/release/CI administration and legacy
finalization are separate operations with their own owners and authority.

## Propose

1. Read selected current bytes, relevant sources, ownership and project intent.
   Identify the contradiction or requested outcome without imposing framework
   defaults or treating a path move as semantic equivalence.
2. Return before/after text or a bounded edit description with affected files,
   source/decision binding, intended behavior, applicability/exclusions,
   consequences, meaningful alternatives and unresolved decisions.
3. Name direct checks useful for the selected change. Use prose in conversation
   by default, or the caller's selected template/export convention below.
   A proposal does not mutate rules or tracking, adopt a change or grant authority.
4. Prepare a Lesson, ADR or standards-promotion candidate only when useful and
   selected. Keep it a semantic candidate until a real receiving operation runs.

## Apply

1. Establish actual task authority for the concrete edit radius. An authorized
   direct request can proceed without first creating a proposal or asking again.
   A proposal, configuration, schema or actor string alone grants no authority.
   Resolve a missing owner-sensitive semantic decision before its affected write.
2. Inspect relevant current bytes, containment, links and concurrent changes.
   Reconcile stale inputs/collisions; preserve other writers' edits and unrelated
   content. Change only authorized project-owned files and in-scope direct
   references. A needed out-of-scope change is an explicit owner handoff.
3. Preserve meaning and full adopted rule text at the existing canonical owner.
   Retain required source/decision references and applicability there. Do not
   duplicate normative statements into a new ledger or shadow entry, weaken
   protections, or manufacture another tool's adoption/effect evidence.
4. Read back actual changes and perform the narrow authorized project checks.
   Report paths, source/decision references, outcomes, uncertainty and next action.
   Failed, unavailable, deferred and not-run checks are not passed. A diff,
   commit or syntax check is not independent review, runtime effect or provider
   acceptance. Execute no check whose side effects exceed the authorized scope.

These instructions provide no generic lock, compare-and-swap, rollback or
multi-file atomicity. On interruption or unexpected changes, report the actual
partial state and remaining work. Do not overwrite newer external changes to
restore a presumed baseline. Read back uncertain writes before deciding a retry.

## Necessary semantic state

Use the project's existing rule and decision owners; create no second
customization catalog, ledger, acceptance packet or universal rule engine.
Keep the full effective statement with its canonical rule owner. When required,
retain semantic identity, material baseline, reason for extension/override,
applicability, decision evidence and real review/expiry obligations with the
existing decision/exception owner. Do not invent a maintenance schedule.

No rule change means no customization event. If no decision store exists, an
explicit user/task decision can support a bounded edit; retention follows actual
project requirements and requested output. Missing intent, adoption or precedence
cannot be supplied by a filename or fabricated row. Installed versions/digests
stay with the installation owner instead of a duplicate semantic inventory.

Keep candidate, accepted knowledge, proposal, owner adoption, actual rule bytes
and effective state distinct. Accepted knowledge alone is not a normative rule.
Proposed text proves no runtime consumption; matching rule bytes alone prove
neither adoption nor effect. An authorized rule edit follows the project process
without claiming any unobserved acceptance or effect.

## Output and existing formats

Default to conversation prose with scope, proposed or actual changes, sources,
limits/checks and next action. Caller templates are inert presentation, not
permission or evidence. Expose unsupported fields or conflicting instructions
instead of inventing approval, execution or identity facts.

Explicit export uses a selected project-owned destination. Resolve a missing
path from the project convention or prepare the content and seek the destination.
Check containment, links, existing contents and authority before writing; preserve
unrelated work and final records, reconcile collisions, and read back the result.
Follow selected tracking and actual project policy without adding a package-wide
workflow, assessment, branch, Issue, index or receipt requirement.

For a selected structured format, establish its version, existing owner, public
operation, destination and lifecycle intent. Map semantic content into supported
fields; let that owner handle identity, writing, read/query, validation,
finalization, versions and migrations. Preserve IDs, creation time, subjects,
final conclusions and supported revision/successor relationships. Unsupported
contracts yield prose/mapping while records stay intact. Do not create a new
assessment family, parser, allocator, query store, finalizer or arbitrary patch.

## Optional knowledge handoffs

Neither a knowledge tool nor the auditor is required to propose/apply a selected
edit. Choose a handoff only for useful learning, a decision with alternatives,
or a proposed existing-rule change; do not automatically create all three.
Before invocation, read the receiving installed version's public operations and
requirements. Use actual task authority, explicit project/package/configuration
and write roots, real queries and current digests. Do not import private code,
configure/install another package implicitly or fabricate a request snapshot.

The following sequences describe the public ADR 0.1.0, Lesson 0.2.0 and
standards-promotion 0.1.0 contracts. Resolve the selected installed version before
using them; an incompatible or missing capability leaves a useful semantic
candidate and a handoff marked not executed, without an automatic installation.

| Destination | Useful candidate | Public handoff and limit |
| --- | --- | --- |
| ADR | Context, drivers, at least two real alternatives with benefits/costs, consequences, evidence and applicability/exclusions | Use actual `query` and a new-identity decision before `create`; `revise` uses an actual draft reference/digest. Later `decide` reads real configured project decision evidence. Acceptance is not implementation or rule adoption. |
| Lesson | Observation, evidence, conclusion, honest confidence, applicability/exclusions and follow-up | Use actual `query` and a new-identity decision before `create` or explicitly selected `derive`; revise only supported candidate state using its real digest. Later `accept` reads real project decision evidence. Accepted knowledge is not a rule; v1 remains read-only history. |
| standards-promotion | Existing target rule and baseline, complete replacement text, rationale, applicability, sources and conflicts | Use actual `query` and a new-identity decision before `propose`; let the owner capture selected config/target/source bytes. Later `reconcile` observes adoption source, rule bytes and effect source separately. Proposal operations cannot edit the rule or generate their own adoption/effect evidence. |

Inspect actual query results before selecting a new identity; use the same query
selection and returned query digest required by the receiver. Partial query
results are not absence proof and require the receiver's explicit partial-result
decision. Revisions use the actual current record digest, not a proposal subject
digest. The receiving public tool generates record identities and snapshots;
report only returned references/digests/outcomes. Do not substitute placeholder
hashes, homemade query decisions, generic JSON patches or invented success.
Uncertain/failed writes require read-back before retry or a completed-handoff claim.

Promotion requires an existing target; new-rule creation follows the project's
explicit process. Never create a dummy rule to satisfy a tool. Conversation-only
content is not a file snapshot: a caller-authorized export within selected
evidence roots may supply bytes; otherwise retain the semantic candidate.
ADR/Lesson evidence references are inert and do not verify their cited sources.

A later public observation is distinct from historical inspect/render output.
Keep proposal, owner adoption, observed actual rule content and declared effect
separate. Promotion's effective result means observed project-declared effect,
not proof of runtime consumption or enforcement. Do not author adoption/effect
records merely to make reconciliation pass.

## Existing policy and recovery

Selecting these instructions does not retire active source/project policy,
historical or finalized assessments, customization ledgers or legacy recovery
contracts. Preserve their identities, conclusions, current bytes and original
supported recovery ownership until an explicit authorized transition. Encountered
pending transactions block the affected transition; do not resume, convert,
clear locks or delete journals through this package.

Source authoring/assessment tooling and unresolved source work remain with their
current owners. Installation compatibility and migration remain with the selected
installation owner. Absence of known old records is not proof their duties can
retire. Follow actual project-required review/tracking without turning optional
maintenance into a prerequisite for ordinary feature, review or knowledge work.
